# Twinfold MVP定義

> ステータス: M0意思決定ベースライン（残課題はIssueで継続管理）
> 決定日: 2026-08-17
> 対象: M1 Devnet MVP〜M4 Closed Beta
> 上位文書: [product-requirements.md](./product-requirements.md)

## 1. MVPの目的

MVPは、機能を一通り作ることではなく、次の事業仮説を5〜10名の招待ユーザーと実物3〜5枚で判定するためのものとする。

> 鑑定済みのポケモンカードを、物理保管とオンチェーン所有権で結び、手元になくてもVision Proで展示できる体験には、購入・保有・redeemの手間とリスクを上回る価値がある。

最重要仮説は「XR展示に継続利用意向があるか」。次に「鑑定・保管・redeemの説明を信頼できるか」、最後に「限定在庫でも採算の見込みがあるか」を検証する。MVPでは市場規模や大規模流動性を証明しない。

## 2. 対象ユーザーと対象アイテム

- 招待ユーザー: Web3ウォレットを自力で扱えるポケモンカードコレクター、5〜10名
- パイロット在庫: Twinfoldが調達する鑑定済みポケモンカード、合計3〜5枚
- 鑑定基準: MVPではPSA等、証明番号をオンライン照会できる第三者鑑定済みカードを優先する。鑑定会社は仕入れ前に1社へ統一する
- ユーザー預託: 対象外。Twinfold主導の調達だけに限定する
- 対象地域: 日本国内の保管・配送に限定する

MVPはポケモンカード1カテゴリに限定する。既存競合が強いことは承知した上で、供給量、相場、鑑定番号照会、規格化されたスラブにより、Vault・mint・所有権反映・XR・redeemの縦切り運用を最短で検証する。原画・セル画への拡張可能性はMVP後に判定する。

## 3. MVPのスコープ

### 必須

- 鑑定済みカード、鑑定会社・証明番号・グレード、NFC ID、Vault保管場所、NFTアドレスを1枚単位で追跡できる
- 高精細スキャン原本と表示用画像を作成・保管できる
- Solana devnetでMetaplex Core NFTを再現可能な手順でmintできる
- WebでPhantom接続、所有NFT一覧、アイテム詳細、redeem申請が使える
- プライマリ販売は招待制で実施できる。セカンダリ売却は外部マーケットへの導線と所有権反映を検証する
- Vision Proで所有する3〜5枚を空間ギャラリーに配置し、鑑定情報を確認できる
- 売却またはredeem後、旧所有者のWeb・Vision Pro表示から対象が失効する
- redeem申請、本人・所有者確認、発送、受取確認、burn、監査ログまでを一度以上ドライランできる
- 保管中の事故、誤発送、二重申請、burn失敗時に停止・復旧できる

### MVPでは行わない

- iOS / Androidアプリとフィジカル×XR記念撮影
- ユーザー所有品の預託受付
- 自社セカンダリマーケットプレイス
- 海外配送、多通貨、法定通貨の本番決済自動化
- 大量在庫、ガチャ、動画、SNS投稿、オクルージョン
- 鑑定番号照合、倉庫作業、配送の完全自動化

iOS / Androidの記念撮影は有望な次段階の仮説だが、MVPではVision Proの展示価値と物理・デジタルの排他運用を先に検証する。

## 4. エンドツーエンド業務フロー

### 運営

1. 鑑定済みアイテムを調達し、仕入れ根拠と鑑定情報を記録する
2. 鑑定会社のオンライン照会で証明番号、カード情報、グレードを現物と照合し、照会結果を証跡として保存する
3. 状態を撮影し、高精細スキャンを作成する
4. NFC付きタンパーエビデント梱包を施し、NFC IDと保管場所を台帳へ登録する
5. 管理者が登録内容を確認し、NFTをmintして販売可能にする
6. 購入・移転を検知し、WebとVision Proの展示権を更新する
7. redeem申請を受けたら所有権を再確認し、対象NFTを移転不可として扱う
8. 宛先と料金を確認して発送し、追跡番号を記録する
9. 受取確認後にburnする。burn失敗時は発送済み資産を販売可能へ戻さず、手動復旧する
10. 鑑定・保管・所有・配送・burnの履歴を監査可能な形で残す

### 購入者

1. Webでウォレットを接続し、現物・鑑定・保管・redeem条件を確認する
2. 招待制の購入手順でNFTを取得する
3. WebとVision Proで所有コレクションを閲覧・展示する
4. 保有を続ける、外部マーケットで売却する、またはWebからredeemを申請する
5. 売却時は展示権が新所有者へ移り、redeem完了時は現物を受け取ってNFTと展示権が失効する

## 5. 状態と禁止事項

| 状態 | 意味 | 許可する操作 |
|---|---|---|
| `intake` | 調達直後、確認前 | 編集・却下 |
| `verified` | 鑑定番号・カード・グレードの現物照合済み | スキャン・梱包 |
| `vaulted` | 梱包・保管・ID紐付け済み | mint承認 |
| `minted` | NFT発行済み、未販売 | 販売・運営取消 |
| `owned` | ユーザー所有中 | 展示・売却・redeem申請 |
| `redeem_pending` | 申請受付済み | 取消または発送準備。売却・再申請は禁止 |
| `shipped` | 発送済み | 受取確認・事故対応。売却は禁止 |
| `burn_pending` | 受取確認済み | burn・手動復旧 |
| `redeemed` | burn完了 | 閲覧履歴のみ。展示・売却・再申請は禁止 |
| `exception` | 不一致・事故・処理失敗 | 管理者による調査・復旧のみ |

すべての遷移は、実行者、日時、根拠、前後状態を監査ログへ残す。`shipped`以降はユーザー都合の取消を受け付けない。MVPではre-vaultを扱わない。

## 6. 成功指標と計測

| 検証対象 | 指標 | MVPの成功基準 | 計測方法 |
|---|---|---:|---|
| 縦切り体験 | 招待ユーザーの購入相当操作からVision Pro初回展示までの完了率 | 80%以上 | `purchase_completed` と `xr_first_item_placed` をユーザー単位で突合 |
| XR価値 | 展示体験後に「また使いたい」と回答した割合 | 60%以上 | 体験直後アンケート、5段階の4・5を肯定とする |
| XR利用 | Vision Pro体験者のうち2点以上を配置した割合 | 60%以上 | `xr_item_placed` のユニークアイテム数 |
| 信頼 | 鑑定・保管・redeemの説明を「購入判断に十分」と回答した割合 | 80%以上 | 体験後アンケート |
| 所有権反映 | 移転・burn後に旧所有者の展示から消えるまで | 5分以内、全試行成功 | チェーン確定時刻と `entitlement_revoked` を比較 |
| redeem運用 | 申請からburnまでのドライラン | 1件以上、重大な手動不整合0件 | 状態遷移ログと配送記録をレビュー |
| データ整合性 | 現物・鑑定・NFC・保管場所・NFTの不一致 | 0件 | 全パイロット在庫の棚卸し |
| 採算性 | 1件あたりの直接原価と粗利見込み | 全費目を記録し、赤字要因を説明可能 | 仕入・鑑定・梱包・保管・配送・チェーン費用を台帳化 |

補助イベントは `wallet_connected`、`collection_viewed`、`redeem_requested`、`shipment_confirmed`、`burn_succeeded`、`burn_failed`、`exception_opened` とする。ウォレットアドレス以外の個人情報は分析イベントへ送らず、配送先とは分離する。

## 7. Go / Conditional Go / No-Go

- **Go**: 縦切り、XR価値、信頼、所有権反映、データ整合性の全基準を満たし、重大事故がない
- **Conditional Go**: XR価値または完了率だけが未達で、原因と4週間以内に検証できる改善案が特定できる。対象を増やさず再テストする
- **No-Go / Pivot**: 鑑定・保管への信頼が80%未満、現物と権利の不一致、取り返しのつかない誤burn・誤発送、または直接原価を説明できない
- **法務停止条件**: 古物営業、NFT販売、寄託、著作物画像のXR表示のいずれかについて、専門家または所管窓口から現行設計では実施不可と判断された場合はClosed Betaへ進まない

## 8. M0完了条件

M0は次を満たした時点で完了とする。実装、契約、許認可取得そのものは後続マイルストーンの成果物とし、M0では判断・担当・期限・停止条件が記録されていればよい。

- [x] 最重要仮説、対象ユーザー、対象カテゴリ（ポケモンカード）、対象地域を一つに絞った
- [x] 必須機能と明示的な対象外を定義した
- [x] 購入、展示、売却、redeemの正常系と主要異常系を定義した
- [x] アイテム状態と禁止操作を定義した
- [x] 成功指標、イベント、Go / No-Go基準を定義した
- [x] M1〜M4の実装Issueへ追跡できる
- [ ] 鑑定番号照合、Vault、保険、配送、古物営業・NFT・寄託・カード画像の著作権の各項目に、暫定方針、確認先、担当、期限、停止条件がある
- [ ] M1着手に必要なAPI / PostgreSQLの採用先とシークレット管理方式が決まっている
- [ ] アカウント親Issueの完了条件をM0に必要な子Issueだけへ限定するか、後続マイルストーンへ移す

未完3項目はGitHub milestone `M0: MVP定義` の #17、#10、#12で管理する。
